Four integration points: ① an identity in Entra, ② an entry in the registry, ③ telemetry through the Observability SDK, and ④ data security through the Purview SDK. The agent keeps running where it is. Only identity, telemetry and the Purview API calls go to Microsoft.
Build order (left column, top to bottom): 1 Entra integration comes first (the A365 CLI creates the blueprint, agent identity and registry entry, and the app uses MSAL OBO at runtime), then 2 the Observability SDK, and 3 the Purview SDK last.

Talk track: the prompt and the response go from LangGraph to Purview through the Purview SDK (processContent), before the LLM runs and before the answer is shown. That's where DLP decides allow or block. OpenTelemetry carries activity telemetry to Defender, Purview Audit and the admin center, but it does not evaluate or enforce prompt/response policies.

Why three objects? The blueprint is the template and credential holder, and it carries the inheritable permissions (Purview SDK and Observability scopes) that every agent identity gets. The agent identity is the runtime principal. Blueprints can't do interactive sign‑in, so a normal app registration signs the user in.

Two separate channels: the Purview SDK calls carry the prompt and answer text and return a verdict. The OTel spans (invoke_agent, chat, execute_tool) carry gen_ai.agent.id, gen_ai.conversation.id, microsoft.tenant.id, user.id / user.email and client.address for Defender, Purview Audit and the admin center.
